# EXP Lab 平台管理与使用规范

文档版本：1.0  
整理日期：2026-09-19  
适用对象：平台管理员、业务负责人、应用负责人、实验创建者和研发接入人员  
实现基线：当前仓库 v23 前端交互原型

本规范约定应用、参数、层域、受众和实验的管理责任及变更要求，使不同团队能够共享实验基础设施，同时保持参数归属、分流和执行一致。指标体系、统计方法及效果分析规范不在本次范围内。

文中的“必须”表达采用本规范后的管理要求。标为“原型已校验”的规则由当前本地代码实施；标为“组织执行”的规则需要团队落实；标为“生产建设”的能力尚未接入真实后端，不能把本规范当作现有权限、审批或运行保障已经生效的证明。

相关文档：[产品设计](./01-产品设计.md)、[技术方案](./02-技术方案.md)、[平台使用手册](./03-平台使用手册.md)。

## 1 管理边界与责任

应用或服务负责参数的业务含义与执行，域负责划分流量，参数层负责划分参数作用域。组织、团队、服务调用链和层域树分别表达不同关系；服务拆分、合并或扩容不应直接触发实验层域重建。

### 1.1 职责分工

以下为建议采用的组织职责；当前原型没有真实登录身份和 RBAC。界面的默认负责人是演示信息，不代表权限已经授予。

| 角色 | 主要责任 | 必须参与的变更 |
| --- | --- | --- |
| 平台管理员 | 维护根结构、全局分流协议、环境边界、发布与恢复机制 | 根级隔离策略、随机化协议、生产平台发布 |
| 业务域负责人 | 管理业务范围、域内资源、跨团队参数划分 | 新建子域、参数层调整、临时资源延期与清理 |
| 应用负责人 | 维护应用接入及参数定义，验证代码能够执行参数 | 新参数登记、执行依赖变化、跨服务联动 |
| 实验负责人 | 编写实验目的、固定参数集合及各组取值，跟进全生命周期 | 提交、启动、暂停、结束以及后续参数收敛 |
| 研发接入人员 | 实现配置读取、上下文传播、执行版本记录与故障回退 | SDK 接入、网关委托决策、模型或索引版本切换 |
| 审核人员 | 核对影响范围、变更版本、参数与流量合法性 | 生产审批与高风险资源变更 |

同一个人可以承担多个职责。生产环境建议对根结构调整、跨业务参数迁移和高风险发布设置独立复核；具体授权矩阵由组织确定并在后端执行。

### 1.2 实现与执行方式

| 规则 | 当前执行方式 | 生产要求 |
| --- | --- | --- |
| 参数所属服务明确，标签属于该服务 | 原型已校验 | 后端重复校验资源访问权限 |
| 同域内激活参数完整且唯一归层 | 原型已校验 | 在同一事务中校验并保存拓扑版本 |
| 同层候选桶冲突 | 原型按有效受众条件校验 | 并发预留、提交及发布时统一校验 |
| 根域仅保留全参数路由层 | 原型已校验 | 保留结构约束与管理员变更权限 |
| 负责人、长期或临时及到期日 | 原型支持字段及日期校验 | 关联真实组织身份、提醒和管理流程 |
| 生产审批、审计、机器凭证、发布回滚 | 生产建设 | 不能依赖前端按钮或本地存储保障 |
| 临时资源定期复查、跨团队评审 | 组织执行 | 后续可用任务与审批流程辅助 |

## 2 应用与参数规范

### 2.1 应用登记

1. 按稳定部署或参数执行责任登记应用／服务，填写可识别的名称、服务标识、负责人和说明。
2. 前端、后端、策略、网关是应用属性；创建实验时不再选择实验所属端。
3. 开发、测试和生产分别维护接入配置。委托决策只能选择同环境的网关／BFF，禁止循环委托。
4. 接入配置保存不等于接入成功。当前状态保持“待验证”，上线前需要真实通信、鉴权、版本和执行验证。
5. 参数由实际拥有业务定义与执行责任的服务登记，不能为了方便选参虚构一个“万能服务”。

生产环境还应登记值班联系人、配置兼容范围和业务回退方式。这些属于接入清单建议，不是当前表单必填项。

### 2.2 参数命名与粒度

参数 Key 当前在整个工作空间唯一。建议使用稳定的小写业务命名，例如 `recall.home.config`、`ranking.home.model`，名称改变业务语义时使用新 Key，避免让历史实验含义发生变化。上述名称为规划示例，并非当前内置参数。

参数应对应一个可以清楚定义、独立读取和验证的配置单元：

- 开关、超时、阈值等使用普通标量参数。
- 需要共同生效的召回路配置、场景权重、过滤策略集使用对象或数组参数。
- 经常独立试验的配置应考虑独立顶层 Key；只有业务能够独立消费时才拆分，不能只为绕过层归属而拆 Key。
- 避免把整个公司的所有场景合成一个巨大对象。它会把实验选择、层归属和执行变更都绑定到同一个 Key。

当前参数归属与实验选参以顶层登记 Key 为单位。`recall.home.config.routes.itemcf.weight` 是该参数内部的 JSON 路径，不是可独立归层的参数。对同一个对象的不同字段做实验，仍要遵守该对象所属层的互斥规则。

参数定义必须包含明确类型、默认值、负责人和业务说明。JSON 必须使用有限数值，不能依赖 NaN 或 Infinity。当前支持 string、number、boolean、object、array；字段 Schema、取值范围、定义版本发布及定义编辑／删除尚未提供。

### 2.3 先登记 再归层

参数登记只写定义、应用归属与应用标签，进入“待归层”。登记阶段不要求选择层，也不会自动扩张已有层的有效作用域。

首次归层必须完成所有受影响域的唯一分配：从根路径向下，在多层域选择一层；单层域自动承接；所选层的子域继续继承并进行分配。整份配置校验通过后才激活参数，未完成归层的参数不能用于新实验。

“待归属服务”与“待归层”是两个问题。历史参数必须先确认真实服务，不按 Key 前缀自动猜测归属；服务已明确也不代表已完成参数层分配。

### 2.4 参数标签

标签只在所属应用内创建和维护。不同应用可以使用相同标签名，但它们是不同标签对象。跨应用批量选参时先选择应用，再使用该应用标签筛选；切换应用不丢弃已选参数。

建议标签表达场景或用途，例如“首页推荐”“召回”“缓存”。标签不表达运行权限、不分配流量，也不代替参数层。实验提交时固化 `parameterKeys`，后续增删或改名标签不能自动修改已有实验的参数集合。

### 2.5 参数变更与回收

已激活参数不能退回待归层来绕过保护。当前通过新建层转移参数时，只允许同域内未被未结束实验使用、没有子域继承依赖的参数，原非空来源层必须至少保留一个参数。

未结束实验的保护范围包括历史正式 draft、待审核、运行和暂停状态；这与是否预留桶不同。处理迁移阻塞时应先清点引用，再制定变更计划，不能直接改浏览器存储。

当前不支持参数删除、服务归属迁移和运行中拓扑迁移。生产建设应提供引用清单、兼容期、迁移前后快照和回退验证，再开放相应操作。

## 3 层域规划规范

### 3.1 建立稳定结构

推荐的规划顺序是：

1. 明确工作空间包含的业务参数和真实流量入口。
2. 在根路由层下规划常规重叠流量与需要完整隔离的流量分支。
3. 在重叠域内按可以独立试验的业务配置责任划分参数层。
4. 对经常跨多个配置责任联动的业务，在覆盖相应参数的共同父层下预留复用的联动隔离分支。
5. 最后在已有层中创建实验，避免每次实验都新增层或域。

根域已锁定唯一的全参数路由层；任何团队都不能为了组合参数在根域再加普通层。跨应用参数可以属于同一个参数层，一个应用也可以有不同参数分布于不同层，关系由参数表达。

### 3.2 新建层与新建域的判断

| 业务需要 | 优先选择 | 必须满足的条件 |
| --- | --- | --- |
| 改同一层的一组参数 | 在该层建实验 | 参数都已激活，存在合法桶分配 |
| 同一批用户并行运行不同参数实验 | 在重叠域内划分稳定参数层 | 参数集合互不重复且完整覆盖域范围 |
| 为一批参数隔离一部分流量继续试验 | 在覆盖它们的父层下建子域 | 子域范围继承父层，不得扩张 |
| 跨层参数需要同组联动 | 优先使用覆盖这些参数的既有隔离池 | 不能直接把其他层的参数加入当前实验 |
| 找不到合适的跨层隔离池 | 先做拓扑设计与依赖评审 | 不复制参数、不临时新增根层 |
| 单次活动或探索项目 | 复用已有层；确需域时标记临时 | 填写负责人和预计结束日 |

创建子域时，自动生成一个承接全部继承参数的“初始参数层”。需要并行实验时，再在合法重叠域中按业务新增、拆分参数层。空层可作为待配置结构保存，但不参与分流，空父层不能创建子域。

非重叠域及其下游分支保持单层结构。在一个普通重叠域的某个参数层下面建立非重叠子域，只隔离该参数分支，不会停止祖先域中其他并行层的实验。需要更大范围隔离时，隔离入口必须放在能够覆盖相应参数的共同父层。

### 3.3 防止层域失控

每个新层或子域的申请应说明用途、参数范围、不能复用现有资源的原因、负责人、期限和预期实验类型。跨服务不是新建域的充分理由，参数很多也不是新建多个层的充分理由。

建议各业务域建立资源清单并在项目结束和定期复查时检查：空层、长期没有实验的层、已超期临时域、缺少负责人的历史资源，以及重复承担同一业务目的的隔离池。配额和审批阈值应依据业务规模设定，不把演示流量比例当成企业统一规定。

层域结构应尽量浅。当前引擎域递归上限为 16 级，这是技术保护边界，不是建议规划深度。新增嵌套之前先说明为什么现有层加受众条件不足以表达需求。

禁止通过修改隐藏字段、复制同义参数、清理 localStorage 或重置用户身份绕开合法性检查。历史资源整理应保留引用和分配记录，不能以整理页面为由让正在运行的实验重新分桶。

### 3.4 推荐系统与微服务示例

下图是一种规划示例，比例仅用于说明。实际原型已经存在默认演示拓扑，不能在有依赖时直接迁移成此结构。

```text
默认域
└─ 默认路由层  工作空间全部激活参数
   ├─ 常规重叠域  示例 80%
   │  ├─ 展示参数层
   │  ├─ 交易参数层
   │  └─ 推荐决策层  召回服务 + 过滤服务 + 排序服务的相关参数
   │     ├─ 推荐常规子域  父层的 90%
   │     │  ├─ 候选集层  召回与需共同调整的业务过滤参数
   │     │  ├─ 排序层    粗排与精排参数
   │     │  └─ 结果编排层 重排与展示编排参数
   │     └─ 推荐联动子域  父层的 10%  非重叠
   │        └─ 推荐全参数层
   └─ 全链路非重叠域  示例 20%
      └─ 工作空间全参数层
```

推荐常规子域的名义全局比例为 80% × 90% = 72%，推荐联动子域为 8%。推荐分支中的多个层复用到达该域的流量，不再把 72% 按层数量平分。受众条件会进一步限制实际符合资格的用户，不能把名义比例直接视作实测人数。

推荐联动子域可组合它继承的召回、过滤、排序参数，并且与推荐常规子域互斥；同一用户仍可能参加常规重叠域中的展示实验。若需同时改变推荐、展示和交易参数，应评估全链路隔离分支的适用性。

这里的“候选集层”可以跨召回服务和过滤服务。排序服务的不同场景参数也可分属不同层，前提是它们是不同登记 Key，并且业务执行能够独立。多个召回路一般是配置对象中的策略条目，不应每条召回路都建立一个参数层。

安全与合规底线过滤应由业务系统保证，不能因为有实验能力就允许实验配置绕开。

## 4 流量与受众规范

### 4.1 正确理解流量

每层固定 10,000 个桶，桶编号 0–9,999。申请 10% 等价于申请该父层坐标内 1,000 个桶，平台可组合多个空闲段，不要求连续。

不得只根据层卡片的总体使用量判断某个受众还有多少流量。申请的可用桶需要把全部祖先条件、当前受众、子域占用和预留实验一起计算。同一桶坐标只有在固定资格条件可证明互斥时才能复用。

| 实验或资源状态 | 当前是否预留桶 | 当前是否输出实验参数 |
| --- | --- | --- |
| 编辑中的本地草稿 | 否 | 否 |
| 历史正式实验 draft | 否 | 否 |
| 待审核 review | 是 | 否 |
| 运行 running | 是 | 是，且需要命中桶和受众 |
| 暂停 paused | 是 | 否 |
| 已完成 completed | 否 | 否 |
| 已创建子域 | 是 | 子域自身不输出实验参数，进入后继续分流 |

暂停用于暂时停止生效，不能当作回收流量操作。域的预计结束日期也不会自动释放桶。生产系统的暂停和结束动作必须配合配置发布、生效确认及历史记录管理。

### 4.2 受众定义

画像属性描述用户或入组时的事实，实验参数描述系统要执行的配置，两者分别登记。画像属性不要求填写来源应用；需要定义类型、取值和清楚的业务口径，真实属性采集责任在生产接入时另行落实。

受众可以使用 AND／OR 组合，当前最多 3 层条件组、30 条规则。创建时检查条件自身、与祖先条件的交集及相关受众关系；域或实验中的快捷创建还会检查申请流量是否可分配，最终提交前再检查。

普通受众重叠不属于创建错误。只有配置了可能同时匹配的候选且桶坐标相交时才构成分配冲突。未知或证明复杂度超限不视为互斥；当前互斥推导的分支组合上限为 64，超过上限仍可求值完整条件树，但不能凭此复用桶。

### 4.3 资格与版本

域和实验引用固定的受众版本。新版本不能静默替换旧引用；有效条件为全部祖先条件与当前受众取交集。条件不能把流量扩张到祖先域之外。

在当前原型，同一 `user_id` 使用首次保存的固定资格快照；缺失字段不视为满足条件，后续也不能为旧用户补填字段来改变资格。生产系统必须明确快照命名空间、生效时点和版本生命周期后，才能提供同等保证。

未命中受众不会换桶，也不会从其他区间补量。这部分名义桶并不等于实际实验参与者。可通过合法的受众互斥复用提高利用率，但不能以补足人数为由改变分桶语义。

## 5 实验配置规范

### 5.1 实验范围

一个实验明确一个所属域和层、一个固定参数 Key 集合，以及 2–20 个分组。所有参数必须属于选中层的激活作用域，且服务归属明确。涉及应用与负责人由选参自动汇总，不再配置前端、后端或算法实施矩阵。

一个跨服务联动方案应在同一个实验的分组中配置各服务对应参数。同一组标识代表同一方案；不能给三个服务分别创建三个实验后，仅凭相同百分比假定用户始终进入同组。

参数组合约束功能已下线。保留类型、Key 完整性、归层、受众、分组比例和流量校验。必要的模型兼容、依赖可用性及执行前置条件由接入责任人检查，后续生产建设再提供统一校验，不恢复为隐藏的旧规则。

### 5.2 分组与长 JSON

每个实验恰好有一个对照组，每组权重为正且总和为 100%。分组使用稳定 ID，不能把显示名称当作跨服务分组标识。调整组顺序、权重或随机化规则可能改变组边界，生产运行期间必须走版本变更流程。

所有组使用相同顶层参数 Key 集合。新增参数时平台用登记默认值补入初值，已有取值保留。当前各组独立保存完整 JSON，不存在“未填写字段自动继承对照组”的语义。

提交前至少完成以下检查：

1. 查看每个组与对照组的结构差异，确认修改的是预期配置。
2. 检查对象内的场景名、策略开关、召回配额和模型版本，避免复制配置遗留无关差异。
3. 确认严格 JSON 有效，无重复属性和非有限数值；顶层为对象，嵌套深度不超过 32 层。
4. 确认模型、索引等引用为可以复现的版本。生产中不应使用可变的 `latest` 代替明确版本。
5. 由各应用负责人确认参数取值可执行，并记录不兼容或回退时的处理方式。

参数目录和组间差异是只读工具。目录最多展示 5,000 个节点，不代表后面的内容未参与完整校验；数组在差异中整体比较，不能把整段数组变更直接解读为只修改一个召回路。当前没有自动合并、Schema 或补丁应用。

### 5.3 提交与发布

本地草稿不预占流量；正式提交时按最新配置重新校验并预留桶。检查页面通过不保证之后一定还有相同流量，冲突时应重新确认分配。

原型支持待审核、审核及运行状态的演示操作，但没有真实的独立审批身份或生产发布。生产审批必须绑定不可变配置版本和变更差异，配置变更后重新审批。审批通过、配置已发布、所有应用已生效应是可以分别追踪的事实。

运行中的受众版本、参数集合、分组比例与取值、随机化单元或层域路径不能被无记录覆盖。生产变更应评估是否需要新实验或新分配周期，并保留原版本、原因、影响清单和恢复方案。

## 6 微服务执行与接入规范

以下为生产接入要求，当前浏览器模拟器和接入配置页没有实现生产 SDK。

跨服务请求链应约定权威决策点，例如网关／BFF 或推荐编排服务。权威点确定同一实验的分组与配置快照，下游服务读取自己负责的参数，并携带相同的决策身份。

同一个用户可能同时命中多个并行层的实验，上下文因此必须表达“实验 ID → 分组 ID”的集合，不能只传一个全局 `A/B` 标志。只透传 `user_id` 也不足以保证一致；各服务还必须共享正确的环境、分配协议、资格版本和配置快照。

应记录决策 ID、实验与分组 ID、配置 revision、参数包或资产版本、实际执行结果和回退原因。分配、读取参数与实际执行是不同事实；中央决策成功不意味着所有服务执行成功，更不意味着跨服务事务已经原子完成。

使用 OpenFeature 时可以复用评估上下文接口和进程内事务传播能力；跨 HTTP、gRPC 或消息队列的传播仍需接入层实现。[OpenFeature Evaluation Context](https://openfeature.dev/specification/sections/evaluation-context/)

传入系统的外部决策头必须经过验证，内部上下文也要限制大小和传播范围。Baggage 不是认证凭证；不要把完整画像、密钥或不必要的身份信息放入跨服务头。[W3C Baggage 安全说明](https://www.w3.org/TR/baggage/#security-considerations)

各服务必须定义本地快照不可用、版本不兼容、模型加载失败和超时后的回退策略。跨服务方案需要明确“单服务失败后各服务分别回退还是采用共同基线”，并记录混合执行情况；禁止把部分回退记录成完整执行了实验方案。

## 7 资源期限 变更与清理

当前域和层支持负责人、长期／临时及预计结束日期。临时资源必须填有效日期；长期资源不保存日期。到期状态按浏览器本地日期显示，可填写历史日期用于标记已经超期的资源。

子域创建时，初始参数层复制一次子域管理信息，之后两者分别维护，修改子域负责人不会自动修改初始层负责人。

到期只做提示，不会自动结束实验、删除资源或回收桶。建议负责人按以下流程处理：

1. 列出该资源及后代的实验、参数与受众引用。
2. 确认用途是否结束；需要延期时更新预计结束日期并记录原因。
3. 明确结束实验、参数迁移、配置兼容和流量恢复顺序。
4. 在生产变更机制具备后按计划发布并核验，再归档相关资源。

当前没有节点删除、域份额编辑和运行中迁移能力。不得将上面的管理流程理解为原型已经具备“一键回收”。

## 8 数据保存与故障处理规范

当前数据保存在浏览器 localStorage，按协议、主机和端口隔离。`localhost:5173` 与 `127.0.0.1:5173` 是不同来源，二者的数据不会自动同步。更换浏览器、清理站点数据或无痕会话结束可能导致本地配置无法继续使用。

草稿保存支持 revision 检查，但 localStorage 不提供跨标签页原子事务、跨设备共享或完整数据备份。遇到冲突应保留当前输入，使用界面提供的另存副本、导出或加载最新版本处理；不建议直接刷新覆盖未保存内容。

正常参数编辑器中的 JSON 导出只包含当前组源码，不是整个平台备份。完整草稿导出仅在相应错误或冲突恢复入口提供。需要团队共享和可靠恢复时，应先建设服务端持久化、权限和备份能力。

| 现象 | 应采取的动作 | 不应采取的动作 |
| --- | --- | --- |
| 参数不能加入实验 | 检查服务归属、待归层状态及所选层范围 | 复制同义 Key 绕过归属 |
| 流量申请失败 | 检查有效受众、预留实验和子域占用 | 只看名义余额或要求连续桶 |
| 新建层被阻止 | 查看非重叠祖先、子域继承与未结束实验依赖 | 改存储强行转移参数 |
| 用户未命中预期实验 | 从默认域运行完整分流验证，查看首个阻断原因 | 更换用户 ID 直到“看起来命中” |
| 配置保存发生冲突 | 先保留输入，再比较当前与最新版本 | 连续覆盖保存或清空存储 |
| 服务接入显示待验证 | 按生产接入计划建设和验证运行链路 | 把保存配置解释为真实连通 |

## 9 评审与交付检查清单

### 9.1 新增层域资源

- [ ] 用途和参数范围清楚，已说明为何不能复用现有资源。
- [ ] 隔离入口覆盖全部需要联合试验的参数，未误认为能隔离祖先并行层。
- [ ] 同域参数分区完整，来源层和已有依赖受保护。
- [ ] 流量比例以父层为分母，已区分名义比例和符合资格的真实流量。
- [ ] 已填写负责人和期限；临时资源有预计结束日期。
- [ ] 已使用分流验证检查准入、未命中和并行路径。

### 9.2 实验提交

- [ ] 固定参数集合已归层并有明确服务归属。
- [ ] 2–20 个分组，恰好一个对照组，权重总和 100%。
- [ ] 全部分组 JSON 校验通过，差异与实验目的相符。
- [ ] 受众固定版本和祖先条件已检查，没有用未知关系放行桶冲突。
- [ ] 已确认提交时重新分配与预留流量的结果。
- [ ] 生产接入时有跨服务执行一致性、依赖版本和回退方案。

### 9.3 生产能力上线

- [ ] 服务端鉴权与状态机不依赖前端校验。
- [ ] 发布绑定不可变快照，审批绑定具体 revision。
- [ ] 参数归层及桶预留有事务和幂等保障。
- [ ] 多语言分桶、资格、版本与回退行为通过一致性用例。
- [ ] 配置分发、真实执行、紧急停用和恢复过程可追踪。
- [ ] 数据备份、恢复、资源变更及审计责任明确。

## 10 规则依据与维护

本平台以 Google 的递归层域模型作为基础：域划分流量，层划分参数，并可交替递归。根层锁定、10,000 桶、管理字段和本文治理流程是本平台的设计选择，不能归为论文的统一要求。[Tang 等 2010 年论文](https://research.google/pubs/overlapping-experiment-infrastructure-more-better-faster-experimentation/)

当前规则的代码依据包括 [`traffic.ts`](../../src/traffic.ts)、[`parameter-assignment.ts`](../../src/parameter-assignment.ts)、[`service-catalog.ts`](../../src/service-catalog.ts)、[`audiences.ts`](../../src/audiences.ts)、[`experiment-variants.ts`](../../src/experiment-variants.ts)、[`json-parameter-analysis.ts`](../../src/json-parameter-analysis.ts) 和 [`resource-management.ts`](../../src/resource-management.ts)。

修改参数归属、受众资格、桶分配、实验状态或发布机制时，维护者应同步更新本规范及对应技术契约；操作入口变化时同步更新使用手册。历史设计和验收记录保留其当时版本，不作为现行操作要求。
