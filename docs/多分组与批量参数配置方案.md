版本：v23 · 2026-09-16（初稿 2026-09-12）。状态：源码工作台、只读目录与组间结构差异已实现；固定基线、表格、树编辑、schema、导入和发布快照仍为产品提案。

**推荐采用“固定基线 + 各组覆盖”的编辑模型，审核和执行时展开为每组完整参数快照。** 大量普通参数使用表格；少量复杂策略参数提供 JSON 树、源码和路径差异视图。用户主要检查组间变化，不需要重复维护多份大 JSON。

## 1. 当前基础与需要解决的问题

当前参数目录包含 `string`、`number`、`boolean`、`object`、`array` 五类。自定义参数有固定 Key、登记名称、类型、默认值、负责人及说明；对象和数组要求有限、可序列化的 JSON，最多 32 层。目前没有对象内部字段 schema，也不校验策略字段的业务含义。登记默认值是初始化来源，不代表已验证的线上生产值。

参数唯一归属一个应用，标签属于该应用。新登记参数先处于待归层状态，完整归层后才能被实验使用。同一个实验在一个参数层内选择参数，可以涉及多个应用；所有组必须配置相同的顶层参数 Key 集合。普通层控制参数范围，域控制分流及继承范围。上述规则继续有效。

当一个实验有数百个参数、多个分组，并且每组只改动几个普通参数或某条召回策略时，逐组复制全部 JSON 会带来三个实际问题：难以看出变化、容易漏参数、修改公共值时无法分辨哪些组应跟随。把几百个字段全部展开成表单也会增加阅读负担。

设计中的“基线”是配置起点，“对照组”是统计比较角色。两者不能混为一谈：基线不会占用实验流量，对照组是一个实际分组；对照组也可以相对基线有明确覆盖。

## 2. 固定基线的推荐工作流（后续方案）

1. **确定实验参数范围。** 从当前层允许的参数中选择 Key，按实际应用归属浏览。搜索、应用和标签筛选只改变可见项，不改变已选集合。待归层、未登记、未明确应用归属或超出层范围的参数不能混入配置。
2. **选择并冻结基线。** 优先选有来源版本的完整配置快照；也可复制旧实验某组的完整配置，或显式使用登记默认值。确认来源、时间、覆盖 Key 和缺失值后复制到实验草稿。未接入配置中心时，不显示“已同步线上”。
3. **建立 2–20 个分组。** 一个对照组，其余为实验组。给每组稳定标识、名称和权重；权重按平台规则校验合计。新组继承固定基线，也可显式复制某个已有组。复制后是独立配置，不形成组间持续引用。
4. **只填写变化。** 普通参数表格编辑；对象／数组在侧栏编辑。每格区分“继承基线”和“本组覆盖”，显示原值与新值。默认提供“仅看差异”，随时切换完整有效配置。
5. **预检与复核。** 查看所有组相对基线、实验组相对对照组的差异；检查 Key 集合、类型、适用 schema、导入错误及流量配置。视图收起的内容也必须参加检查。
6. **冻结完整结果。** 提交时把基线与覆盖解析成所有分组的完整有效配置，连同来源和定义版本保存。后续模板变化不改变此次实验。

选择基线时只取本实验声明的 Key。模板中有额外参数须列出并明确排除；缺少已选参数则要求补齐，不悄悄读取“最新默认值”。跨应用基线用一个来源清单记录各应用的来源版本，再冻结成同一实验快照；该动作不等于已经保证生产服务同时更新。

## 3. 页面布局与普通参数编辑（后续方案）

参数较多时使用可扩展的宽页面或宽工作区，不在每个分组卡片中重复放整份文本。建议布局：

```text
参数配置  已选 286 Key / 3 应用    基线：推荐配置 v12（已固定）
分组：A 对照 25% | B 召回增强 25% | C 重排 25% | D 组合 25%
搜索 Key / 名称 / 路径   应用：全部   标签：先选择应用
视图：● 仅看差异  ○ 全部   比较：相对基线 / 相对对照组
┌─────────────────────┬────────┬─────────┬─────────┐
│ 参数 / 类型         │ 基线   │ B 组    │ C 组    │
│ ranking.result_limit│ 20     │ 30 覆盖 │ 继承 20 │
│ ranking.strategy    │ 对象   │ 2处变化 │ 1处变化 │
└─────────────────────┴────────┴─────────┴─────────┘
选中策略参数 → 右侧：场景 / 召回路目录 | 树 / 源码 / 差异
底部：286 Key；当前筛选 8 Key；已修改 5 Key；3组通过 / 1组待修复
```

20 个分组不同时挤入屏幕。固定参数列和基线列，分组横向滚动；提供“当前组”“对照组 + 当前组”“选择若干组比较”，隐藏组的错误仍汇总在底部并能定位。大量行使用虚拟列表，但选中状态和编辑状态按固定 Key 与组标识保存。

普通类型采用对应控件：布尔开关、数字输入、字符串输入；枚举下拉仅在存在有效 schema 时提供，不能根据现有几个值猜测枚举范围。数字 `0`、布尔 `false`、字符串 `""` 都是明确的值。空白的编辑中间态不能自动转换为其中任何一个。

每个覆盖有“恢复基线”操作。把某个值设为与基线相同，与声明“继承基线”在草稿语义上不同：前者仍是显式覆盖，基线更新预览时不会自动跟随。界面应显示这一状态，不仅凭值是否相同推断继承。

“批量设值”“复制到分组”“恢复基线”先明确目标 Key 和组，复核影响数量后一次应用。筛选结果不能充当隐式全选范围；对隐藏的已选项须说明数量。批量修改失败时保留原草稿。

## 4. 策略 JSON：场景与召回路是内部结构

以下是**设计示意**，不代表当前线上配置或已登记参数。假设 `ranking.strategy` 是推荐排序应用下的一个 `object` 参数：

```json
{
  "schema_version": 1,
  "scenes": {
    "home_feed": {
      "recall": {
        "routes": {
          "popular": { "enabled": true, "limit": 100, "timeout_ms": 30 },
          "user_cf": { "enabled": true, "limit": 150, "timeout_ms": 45 },
          "semantic": { "enabled": false, "limit": 100, "timeout_ms": 50 }
        },
        "route_order": ["popular", "user_cf", "semantic"],
        "dedupe": true
      },
      "rank": { "model": "rank_v5", "max_candidates": 300 }
    },
    "detail_related": {
      "recall": {
        "routes": {
          "item_cf": { "enabled": true, "limit": 80, "timeout_ms": 35 },
          "same_category": { "enabled": true, "limit": 60, "timeout_ms": 25 }
        },
        "route_order": ["item_cf", "same_category"],
        "dedupe": true
      },
      "rank": { "model": "related_v2", "max_candidates": 120 }
    }
  }
}
```

例如 B 组仅启用首页的语义召回，并把候选数上限改为 400；C 组仅修改首页排序模型。对 B 组显示：

```text
ranking.strategy
  /scenes/home_feed/recall/routes/semantic/enabled   false → true
  /scenes/home_feed/rank/max_candidates             300   → 400
  detail_related                                  无变化
```

界面左侧“首页信息流 → 召回 → semantic”是 JSON 内部路径导航，名称可来自 schema 的展示元数据；没有 schema 时展示原始字段名。内部路径使用带转义规则的 JSON Pointer，不能用简单点号拆分，避免字段名含点号、斜线时发生歧义。

这里有三种不同的组织方式：

- **应用归属：** `ranking.strategy` 只有一个维护应用；前端或其他服务消费它不会新增所有权。
- **应用私有标签：** “首页推荐”等标签用于筛选整个参数 Key，只属于该应用。切换应用不共享同名标签。
- **JSON 内部场景和召回路：** 用于定位同一个参数内部的路径，不成为平台标签、不参与归层或分桶，也不自动注册为独立 Key。

如果首页与详情场景将长期独立实验、独立发布或分到不同参数层，应评估拆成 `ranking.home_strategy`、`ranking.detail_strategy` 等独立参数。不能仅因为编辑器能展开字段，就把所有叶子拆成几百个 Key。一个对象仍是当前平台的最小归属和覆盖单元；它的两条内部路径不能因此被不同层分别覆盖。已有对象拆分须作为明确的参数与消费代码迁移，不在导入时自动进行。

## 5. JSON 树、源码和差异的行为

**v23 已实现的增量。** 当前编辑对象是整个分组 JSON，提供“源码编辑”和“分组差异”两个视图，共享完整原文草稿。CodeMirror 6 源码独立滚动，专注模式扩大到当前视口；每个分组在本次编辑器会话保留独立光标、折叠、滚动和撤销记录。刷新或重开编辑器只恢复已保存源码，不恢复这些临时记录。

只读目录展示顶层参数及内部对象／数组路径；可按字段、路径、值和登记名称搜索，再按实际应用与该应用的私有标签筛选。切换应用清除标签条件，筛选不隐藏校验范围或裁剪源码。内部路径采用 JSON Pointer，点号 Key 不拆分。目录最多展示 5,000 个节点并提示限制，完整内容继续参与校验与比较，也可通过源码搜索访问。

诊断检查严格语法、顶层对象、重复解码属性、有限数字和最多 32 层嵌套，点击问题定位源码；错误文本继续自动保存。格式化必须先通过校验；导出直接下载当前组完整原文，未完成文本也保留。草稿提交和批量加入参数使用相同严格检查，重复 Key 不会因解析只留下最后值。

组间差异可选择另一个实际分组作为比较对象，显示新增、删除和修改路径及前后值。忽略空白和对象字段顺序，数组整体比较，元素变更与重排均记为数组修改。缺失和 `null` 分开显示；任一组无效时停止比较。差异只读，无复制补丁、自动合并或恢复基线按钮，不会用历史有效值代替当前无效原文。

**后续可编辑树与固定基线方案。** 未来可为同一个复杂参数提供三个视图，共享同一份草稿：

- **树视图：** 懒加载场景和召回路，可按路径搜索；叶子按字段类型编辑。新增或删除字段仅在 schema 允许时开放。
- **源码视图：** 在现有原文编辑能力上，增加与可编辑树的显式同步。错误文本不能在切换视图时被丢弃；树模式应明确提示无法解析，不能将上一次有效对象冒充当前文本。
- **差异视图：** 按“新增、修改、删除、顺序变化”展示路径及前后值；可以选择相对固定基线或某个实际分组比较。对象字段顺序变化不作为业务差异，数组顺序变化必须显示。

未来第一阶段即使编辑某个叶子，草稿也保存该顶层参数的完整覆盖值；JSON 路径差异由前后对象计算。这样不需要先引入复杂补丁执行器。若后续支持路径级覆盖，则必须显式记录设置、删除及恢复继承操作，并使用基线内容校验，不能靠隐式递归合并解释用户意图。

**数组首期统一整段替换。** 不按下标自动合并，不根据 `id` 字段自动去重，不把导入缺少的元素保留在旧数组中。数组的 `null` 元素是真实值，不能用作删除标记。大数组可以分页展示和对比，但保存及校验覆盖完整数组。

示例采用 `routes` 对象按稳定 route ID 定位，并单独使用 `route_order` 表达顺序，便于查看差异。这只是新配置的建模建议，不能自动转换已有服务使用的数组。后续若要按业务 ID 合并数组，需由固定 schema 明确身份字段，并要求唯一 ID、明确插入／删除／重排、预期旧值和冲突策略；缺少这些条件继续整段替换。

## 6. Schema 采用分阶段、显式能力（后续方案）

当前顶层类型及 JSON 合法性校验继续保留。后续可以为复杂参数附加**不可变版本的字段 schema**，但不把本轮移除的任意参数组合规则编辑器重新放回创建实验流程。

首期字段 schema 建议支持：字段类型、必填、枚举、数值范围、字符串长度、对象子字段及是否允许额外字段、数组元素类型和长度。一个对象内部的引用关系，例如 `route_order` 中每个 ID 必须存在于 `routes`，需要明确支持的校验能力；通用字段类型检查不能声称已经验证这种策略业务正确性。

schema 登记时公布支持的关键字。第一阶段不支持的远程引用、任意脚本、复杂条件或自定义函数应在登记时拒绝或标为不可启用，不能忽略后显示“验证通过”。业务校验器若以后接入，应固定版本、返回路径化错误，并独立展示是否执行成功，不能把超时当作通过。

没有 schema 的历史对象允许继续使用“JSON 语法 + 顶层类型”的明确兼容模式，显示“未执行字段级校验”，不能突然套用严格新 schema 而使历史实验无效。给新实验选用 schema 时必须明确版本；添加 schema 或升级版本不会重写旧参数定义及旧实验快照。未来的 schema 引用属于新增数据模型，当前参数定义不可变约束不能被直接改字段绕过。

参数登记默认值、JSON 内部默认值和 schema 的 `default` 注释不能在校验时自动补写。缺失、`null`、空字符串和删除是不同状态；顶层值仍须符合当前参数类型，`object` 不因 JSON 支持 `null` 就允许顶层 `null`。

## 7. 批量导入：先预检，再原子应用（后续方案）

建议第一阶段支持 JSON 文件和结构明确的 CSV，不接受会隐式推断类型的任意表格或 YAML。CSV 至少包含 `group_id`、`parameter_key`、`action`、`value_json`；值用 JSON 语法表达，`"20"` 与 `20` 不等价。对象、数组也可以导入，但复杂策略优先采用 JSON 文件。

导入前明确选择模式：

| 模式 | 文件含义 | 未出现的内容 |
| --- | --- | --- |
| 更新草稿覆盖 | 指定 Key／组的 `set` 或 `inherit` 操作 | 保持原草稿；不能当作恢复基线 |
| 导入完整分组配置 | 文件包含所选组的全部声明 Key | 缺少任意声明 Key 都报错 |

`set` 必须提供值；`inherit` 明确移除该组覆盖、恢复到固定基线，不能附带冲突值。首期不提供“删除本实验顶层 Key”的导入操作；要改变声明集合，走独立选参流程，并对所有组同步确认。对象中的字段删除通过完整对象替换体现。

预检过程：

1. 读取文件，检查编码、格式版本、体积及结构限制；JSON 中重复对象 Key 必须在解析阶段报告，不能接受解析器默默保留最后一个值。
2. 对照工作空间、实验和当前草稿修订号解析稳定组 ID 与固定 Key；未知组、重复目标、未知参数、待归层、跨范围或不明确应用归属均报错，不代用户注册或归层。
3. 严格验证值和固定 schema，不将数字字符串转换成数字，不截断数组，不删未知字段，不用默认值补齐缺项。同一目标的重复或父子路径冲突不采用“最后一条获胜”。
4. 在临时副本中解析所有组的完整配置，检查相同 Key 集合、固定基线完整性，以及所有受影响组。任一错误都不应用；错误列表定位到文件行／JSON 路径、Key 和组。
5. 显示新增覆盖、修改值、恢复继承及对象字段删除数量，并允许展开完整差异。确认面板明确“影响几组、多少 Key、多少内部路径”，不能只展示当前应用筛选下的几行。
6. 点击“应用到草稿”时再次核对草稿修订号、拓扑及参数目录。预检之后发生变化则要求重新预检，不自动覆盖新编辑。通过后一次替换整个候选草稿；存储失败时保留原状态并返回错误。

应用到草稿后可以撤销整个导入批次。它不自动提交审核、占桶或发布。部分行成功、部分行失败会制造难以辨认的组合，首期不提供这一模式。

建议性能验收样本为 1,000 个 Key、20 组和数个较大策略对象；这不是当前已承诺的容量。文件上限和快照上限需在实现前结合浏览器存储实测确定并在界面公布，超限应明确拒绝。若实验完整快照超过本地存储能力，需要后续服务端存储，不能静默只保留差异来绕过容量。

## 8. 快照与后续模板变化（后续方案）

草稿建议记录：选定 Key 集合、固定基线内容与来源清单、各组稳定 ID／名称／权重／对照角色、覆盖值、选用的定义及 schema 版本、草稿修订号。保存时保留完整分组有效值，来源信息和覆盖只是可追溯的编辑信息。

审核使用快照内容摘要或等效一致性标识，把审批结论对应到具体内容。提交后组值、对照角色、分组权重、受众或参数集合变化应走新的草稿修订及审核；已运行实验的变化按平台的阶段／新实验策略处理，不能跟随模板自动变化。本文不新增自动重分桶规则。

“更新基线”必须是显式操作：先固定候选新版本，再对比旧基线、各组覆盖和新结果。继承项可在确认后跟随；显式覆盖保持原值，发生字段删除、类型变化、旧 schema 不兼容时阻止更新并定位。一次确认完整生效，不因刷新或重新打开页面自动重算。

执行侧消费冻结后的完整分组配置及配置版本，不在运行时读取“最新模板 + 覆盖”做动态拼接。这里的完整是指**本实验声明的参数集合**，不包括整个参数目录，也不意味着覆盖其他并行层的所有参数。

完整快照可以确保平台记录的组合明确；跨应用生产一致性仍需要决策结果和版本透传、配置拉取与缓存协议、消费确认、曝光回传及故障回退。当前本地原型没有这些生产保证，不能把编辑器原子保存描述为前后端已同时生效。

## 9. 方案取舍与阶段建议

| 方案 | 优点 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 每组一份完整 JSON | 通用，兼容既有数据，容易导出 | 重复多，公共值维护成本仍高 | v23 现行方式，已增加源码、目录和差异辅助；继续评估基线演进 |
| 所有叶子变成独立平台 Key | 表格检索方便，可单独归层 | 破坏对象边界，登记和维护负担大 | 只按独立实验／发布边界拆 Key |
| 完全由 schema 生成复杂表单 | 有引导，容易定位字段错误 | 依赖高质量 schema，未知结构难兼容 | 后续增强，不作为启动前提 |
| 固定基线 + 各组覆盖 + 完整快照 | 减少重复，差异可审查，运行来源确定 | 需明确继承、合并及版本规则 | 推荐；先顶层覆盖，再增强路径编辑 |

**已交付至 v23：** 多分组、全页草稿与自动保存、长 JSON 源码工作台、专注编辑、只读路径目录、严格诊断与原文导出、实际分组间结构差异。仍以完整组 JSON 为存储模型；这些能力不等于固定基线、可编辑树、字段 schema 或批量导入。

**后续第一阶段：** 在已实现源码与只读组间差异之上，增加固定基线、普通参数表格、顶层完整值覆盖、相对基线的差异与完整配置查看。实现 JSON／CSV 预检、整批应用和撤销；提交仍保存每组完整配置。数组统一整段替换。

**后续第二阶段：** 接入不可变字段 schema，增加可编辑 JSON 树、场景／召回路的业务展示元数据、字段级语义错误与完整 schema 版本追踪。现有目录和路径定位不依赖 schema；后续结合大参数性能样本调整编辑树、列表及限制。

**后续第三阶段：** 有真实需求时再增加外部配置基线来源、按稳定业务 ID 的数组操作、领域校验器和生产快照分发。不先实现任意脚本规则、隐式深合并或可漂移的运行模板。

后续验收至少覆盖：20 组只改少量参数可准确审查；隐藏应用／隐藏组的编辑仍保留；JSON 仅两条召回路径变化可定位；数组重排与删除均显式显示；重复 Key、缺参数、错类型及未知参数整批失败；预检后草稿变化拒绝陈旧导入；存储失败不改变原稿；模板和 schema 新版本不改变已提交或运行实验。用户能导出任一组的完整有效配置并与审核快照逐项对应。
