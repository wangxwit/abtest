## 0. Google 论文事实核验：层、域和参数

来源：Diane Tang、Ashish Agarwal、Deirdre O’Brien、Mike Meyer，*Overlapping Experiment Infrastructure: More, Better, Faster Experimentation*，KDD 2010。[Google 论文页面](https://research.google/pubs/overlapping-experiment-infrastructure-more-better-faster-experimentation/)；[官方 PDF](https://research.google.com/pubs/archive/36500.pdf)。页码均指 PDF 从封面起的第几页。原始站点会跳转 Google 托管地址；本轮 web 工具拒绝重定向后，使用 curl 下载并用 PDF 文本抽取及页面渲染核查。

| 论文事实（不是自研建议） | 原文定位 | 设计含义 |
| --- | --- | --- |
| Domain 是流量切分；Layer 是参数子集；Experiment 是可覆盖零或多个参数值的流量切分 | PDF 第 3 页，§4 | 需要三个实体及参数目录，不能以实验类型替代层或只给层加域名称 |
| 域包含层；层包含实验，也能包含子域；默认域与层覆盖所有流量与参数 | PDF 第 3–4 页，§4 | 完整模型支持交替嵌套；V1 扁平化是显式范围裁剪 |
| 非重叠域是只有一个普通层的域，该层覆盖全部参数；请求至多参加其中一个实验，可改任意参数 | PDF 第 4 页，§4，Figure 2b | 它分走独立流量，可容纳跨既有参数分区的整体方案实验 |
| 重叠域包含多个普通参数层，每层至多命中一个实验，跨层可重叠 | PDF 第 4 页，§4，Figure 2a/b | 每层都可使用该域的流量，不能把各层占用相加当全量占用 |
| 不同域可以对参数采用不同分区；域内普通层对应不重叠参数子集 | PDF 第 3–4 页，§4，Figure 2d | 参数唯一归层的校验作用域是该域普通层分区，不是全平台 |
| 各层 cookie 分流含 layer 标识，以实现独立分配 | PDF 第 4 页，§4 | 共用同一 cookie hash 不能自动视为层间正交 |
| 改变域份额会改变其他域及其实验拥有的流量 | PDF 第 4 页，§4 的 10% → 15% 例子 | 域扩量不是保持运行实验样本不动的常规操作 |
| Launch layer 在默认域覆盖全部流量，有独立参数分区并提供替代默认值；普通实验显式覆盖优先 | PDF 第 4 页，§4，Figure 2c/d | 发布层不能当作第三个互斥流量域；最终取值有固定优先级 |
| 域只采用 user-id / cookie-id 分流；层内分流顺序为 user-id、cookie、cookie-day、random | PDF 第 5–6 页，§4，Figure 3 | 混合分流模型需按顺序实现，V1 可明确只支持稳定身份类型 |
| 命中某分流段但条件不满足的流量标记 biased，不继续分给后续类型 | PDF 第 5–6 页，§4，Figure 3 | 条件筛剩流量不必然是随机样本，不能自动回收给后续随机实验 |
| control 也称 experiment，可在层中设置大规模共享对照 | PDF 第 3 页 §3；第 6 页 §5.2.1 | 平台把 A/B 装入同一 Experiment 是自研管理封装，需说明对应关系 |
| Figure 4 展示 diversion 类型与标准误；Figure 5 展示实验、人员、发布趋势 | PDF 第 7 页 §5.2.1；第 9 页 §6.1 | 层域模型证据主要是 Figure 2–3，不能错用后两图 |

**本平台的实现建议（超出论文或缩减论文范围）。** 当前原型已做默认层下互斥的重叠域 / 非重叠域及递归子域；非重叠域一个全参数普通层，重叠域多个有参数所有权的普通层。单个 Experiment 管理对象包含 A/B variants，保证每请求每层至多一个分流单元。递归域、参数继承、父层共桶及本地新建子域已实现（16级域深度保护）。暂不执行共享对照、混合 diversion 顺序和发布层完整语义，未实现能力不得在 UI 标作可用。

请求路径建议为：稳定身份 → 域分配 → 域内每层实验分流 → 组内 variant → 参数覆盖合并 → 跨服务透传 → 实际执行事件。先域后层是论文模型；A/B variant 封装、跨语言 hash 测试、签名快照和透传协议是自研工程建议。

容量示例（自研 UI 表述）：非重叠域占父层 20%，该域普通层内某实验占 50%，B variant 占实验 50%，则 B 占父层全量 5%。重叠域所有普通层共用同一域流量，但参数互斥归属。禁止把“层内 50%”直接标成“全量 50%”。

启动校验建议新增：兄弟域流量段冲突、非重叠域多普通层、同域普通层参数重复归属、实验覆盖域/层外参数、实验与对照分流方式不一致，以及有活跃实验时直接改变域份额。完整论文还提到可组合数值运算放松单层参数限制（PDF 第 9 页 §7）；本平台 V1 采用覆盖语义，不支持该扩展。

## 1. 核心取舍

建议先落实论文的「域切流量、层分参数、实验覆盖参数」核心，再统一决策协议、身份与分桶规则、曝光和指标契约、治理流程。不同运行时可有不同执行方式；平台还必须保证随机化正确、实际生效可追踪、结果可复现。

| 场景 | 建议执行方式 | 关键约束 |
| --- | --- | --- |
| Web / App 前端 | BFF 或边缘决策后下发用户级配置，SDK 缓存并上报实际渲染/功能触达 | 浏览器不持有服务端密钥或完整敏感人群规则；首屏可 bootstrap，避免闪烁 |
| 后端服务 | 可信环境内 SDK 根据签名配置快照本地决策；同步更新走控制通道 | 请求路径不强依赖控制台或网络分流 RPC；跨语言 golden vectors 验证一致性 |
| 推荐 / 搜索 / 风控等策略 | 同一决策结果关联不可变参数包、模型版本及依赖版本 | 参数做 schema / 范围 / 依赖校验；实际执行版本入日志；先 shadow 后放量 |
| 前后端联动 | 网关/BFF 作为约定的决策权威点，向内部服务透传受信的决策快照 | 同一实验同一请求链使用同一版本；业务不能直接相信客户端提交的分组 |

依据：LaunchDarkly 官方文档区分客户端远端评估与可信服务端缓存规则本地评估，这为上述执行分工提供现成工程模式；具体选型仍应按现有技术栈决定。[SDK 类型与评估方式](https://launchdarkly.com/docs/sdk/concepts/client-side-server-side)

## 2. 统一决策与配置协议（建议）

建议向业务暴露 `evaluate(experiment_key, context, default_payload)` 与 `track_exposure(decision_token, trigger)` 两个分离动作，批量评估作为可选接口。执行位置由 provider 决定，业务不直接依赖各供应商接口。

- 输入：项目、环境、实验 key、随机化单元类型与稳定 ID、受信属性、请求/trace ID、客户端/服务版本；服务端解析受信域层归属。
- 输出：`domain_id`、`domain_epoch`、`layer_id`、`experiment_id`、`allocation_epoch`、`variant_id`、`decision_id`、配置 revision、schema 版本、合法参数 payload、评估 reason、是否 fallback、有效期。
- 评估 reason 至少包含：正常分桶、定向不命中、互斥占用、预览强制分组、实验暂停、快照过期、上下文缺失、schema 不兼容、紧急熔断。
- `allocation_epoch` 是分配设计的版本；配置 revision 是发布版本。不能把每次配置 revision 放进随机 hash，否则普通修改就会重新分组。
- 参数协议使用严格类型及 JSON Schema 类约束。前端样式、服务处理分支、模型/策略参数都关联到同一实验变体；资产本体仍由代码仓库或模型仓库存储。
- SDK 兼容 OpenFeature 风格的评估 API，可通过 provider 降低业务代码耦合；平台自行补充实验分配、曝光、统计与审批能力。OpenFeature 并非完整实验分析引擎。

依据：OpenFeature 定义 targeting key、任意上下文属性以及 transaction context 传播。[Evaluation Context 规范](https://openfeature.dev/specification/sections/evaluation-context/)

## 3. 随机化、层与身份（建议）

1. **随机化单元在启动前冻结。** 普通体验实验选 user_id；未登录体验可选 device_id；团队协作实验选 org_id。请求级单元只适合无持续体验、无跨请求干扰的明确场景。不能按请求分组再把请求当独立用户进行显著性计算。
2. **先域，再层，再组内变体。** 稳定 unit 先决定域；进入重叠域后逐层分流，非重叠域只执行其全参数普通层；随后在平台管理对象内确定 A/B variant。采用规范化字节编码、固定 hash 与边界，跨 SDK 共用测试向量。
3. **域内实验放量与改域份额分开。** 固定域与变体比例时扩大实验准入可保持既有变体。改变域份额会从兄弟域迁移流量，影响旧实验；运行中默认阻止，另经迁移计划、epoch 与受影响实验审批处理。
4. **同域参数分区，层内互斥。** 重叠域普通层之间参数不重叠且独立分流；同一参数不能由该域多个普通层覆盖。非重叠域单层允许全参数组合。分配独立不保证效果无交互；仍需诊断共同命中。
5. **前端/后端/策略是实施范围，不是默认互斥层。** 一个前后端协同实验只创建一个实验、一个分组与多端绑定；不各自建三个实验。
6. **匿名到登录不自动消除身份冲突。** V1 建议每个实验选定 user_id 或 device_id 并贯彻整个周期；device_id 实验在登录后仍携带该设备实验单元。需要跨设备时只纳入有稳定账户 ID 的群体。身份映射不能追溯改写已发生的分组与曝光。
7. **一致性边界写入 SDK 合约。** “同单元、同 epoch、同快照、同受信上下文”才能保证跨端一致；由权威决策点透传可以解决链路上规则快照短暂不一致。身份桥接/sticky assignment 存储留到确有需求后设计，需明确多个旧身份冲突时的取舍。

Google 层域事实以第 0 节的原文定位为准。以下是辅助工程材料，不替代论文模型：Optimizely 对互斥组的说明提醒桶复用可能带来历史处理效应。[互斥实验机制](https://docs.developers.optimizely.com/full-stack-experimentation/docs/mutually-exclusive-experiments)

## 4. 服务透传与配置一致性（建议）

- 内部 HTTP/gRPC 元数据携带精简的决策 token：实验、变体、epoch、revision、决策 ID、签发/过期时间；入口校验签名与项目/环境，移除外部伪造头。
- 优先沿调用链传播该实验的已决策结果，不让下游使用不同配置重新计算。日志与 trace 记录版本，能定位何处产生错组或回退。
- W3C Baggage 可承载跨服务上下文，但它不是认证机制；敏感 ID、完整画像、密钥不放入头，不传播到外部域名；设置大小与条目数上限。
- CDN 缓存键与 SSR hydration 必须纳入实验变体或相应输出版本，避免 A 用户拿到缓存的 B 内容。
- 配置分发使用签名不可变快照、校验、原子替换和最后已知良好版本；观察各区域/SDK 生效 revision 的收敛状态。

依据：W3C Baggage 的安全与隐私章节说明上下文传播会带来敏感信息泄露与信任风险。[W3C Baggage](https://www.w3.org/TR/baggage/)

## 5. 曝光与指标（建议）

明确三件不同的事：**assigned**（随机分配）、**eligible / triggered**（具备被影响机会）、**delivered / exposed**（实际执行/展示）。读取配置不天然等于曝光，策略 shadow 运行也不应记成对用户实际生效。

- 事件最小契约：全局 `event_id`、事件与接收时间、项目/环境、unit 类型与伪名化 ID、domain/domain_epoch/layer、experiment/variant/epoch/revision、decision_id、触发点、实际执行结果、schema 版本。
- Assignment 表保留分析所需的分配记录；曝光日志可批量上报、幂等重试，服务端按 event_id 去重。预览、白名单调试、内部员工和机器人按预先定义规则隔离。
- 对照组与处理组在同一处判断触发条件。不能只分析点击新按钮的人；按钮点击已经可能受处理影响。触发分析要求触发条件不被处理改变，并验证遗漏群体无实验效果。
- 默认主分析采用预先定义入组群体的 ITT 思路，保留分配后失败/回退的单位；补充展示实际执行率和污染率。不能通过删除处理组失败流量制造提升。
- 指标目录固定 owner、业务定义、SQL/DSL revision、来源、随机化 ID 映射、分子/分母、聚合方法、方向、归因窗口、迟到窗口、去重键、缺失与异常值政策。
- 转化率、总量、人均值、比率、分位数使用相应的统计估计方式；方差必须保留随机化单元内相关性，不能把用户的每次点击当作独立样本。
- 实时流用于异常告警；有版本的仓库快照用于正式结论。结束入组后需等待转化窗口成熟与迟到数据补齐，再冻结结果。

依据：Microsoft 建议校验 triggered SRM，并用 triggered-complement 分析验证触发范围；Statsig 的集群实验说明组织级随机化与用户级指标需要考虑分子分母协方差及单元聚类。[触发分析有效性](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-post-experiment-stage)、[集群实验与比率统计](https://docs.statsig.com/metrics/different-id)

## 6. 统计与质量门禁（建议）

V1 先提供可审计的固定周期频率学派方案：预注册一个主指标、少量护栏、MDE、显著性水平、power、预计样本与观察窗口。`alpha = 0.05`、`power = 0.8` 可作可修改默认值，但样本估计须依赖真实基线/方差和单位类型；“运行 7 天”不天然代表有足够证据。

- 页面同时呈现绝对变化、相对 uplift、置信区间、样本量、数据成熟度与业务阈值。显著不等于值得上线，无显著差异也不等于两组等效。
- 多处理组/多个共同主指标在预注册比较族内调整（V1 可采用 Holm）；临时切片是探索性结论。护栏若用于“未显著变坏即安全”的判断，应改成预先定义可接受退化幅度的非劣效判据。
- 中途看图可以用于观测，固定周期普通 p 值不用于随时宣布胜出或延长到显著。需要可提前止盈时另设经过验证的序贯方法，启动前固定方法；严重运行事故的安全停止始终允许。
- SRM 分别监测分配、触发、可分析数据阶段，按真实分配比例及 epoch 核验；分端/地区/SDK 版本帮助定位。连续监测阈值需控制重复告警，不能机械每小时重复一次普通检验。质量严重异常时阻止“胜出”结论，允许修复、解释与安全停止。
- 上线平台前做 A/A、合成事件与历史回放，检验分桶、false positive、数据迟到和跨 SDK 一致性。
- CUPED 是下一阶段能力：只使用处理前协变量，在对应随机化单元上验证覆盖、方差和偏差；不把它当作 SRM 或埋点错误的修复工具。
- 市场供需、网络效应、公共缓存/资源竞争等存在单位间干扰时，普通用户级 AB 可能不适用；集群、地域或 switchback 另立方法，V1 不假装统一自动支持。

依据：Microsoft 将 SRM 作为结果可信度门槛；Statsig 说明普通固定周期检验的提前决策会膨胀误报、序贯检验需调整推断；Microsoft CUPED 文章解释处理前数据的方差降低用途。[SRM 诊断](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/)、[序贯检验与提前决策](https://docs.statsig.com/experiments/advanced-setup/sequential-testing)、[CUPED](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/deep-dive-into-variance-reduction/)

## 7. 故障、发布与企业治理（建议）

**分离设计状态、运行状态、结论状态。** 推荐设计流程：草稿 → 校验 → 待审批 → 已批准。运行流程：未启动 → 小流量观察 → 运行中 → 停止入组/观察窗口成熟 → 已结束；暂停/熔断是可发生的运行分支。结论流程：待分析 → 质量阻断/证据不足/胜出/退化 → 发布或归档。这样“已停止”不会被误解成“结论已成熟”。

- 生产审批绑定具体 revision 与 diff；提交后的更改使原审批失效。实验参数、身份、指标口径、统计方法启动后受版本控制，改变分析设计应开新 epoch 或新实验。
- 故障回退顺序预设为：有效的本地快照 → 允许使用的最后良好快照 → 业务明确默认值。根据风险为配置定义最大陈旧时间。回退事件和实际处理率可见，指标故障不能默默丢弃影响样本。
- 紧急 kill switch 优先级最高；可以绕过普通发布审批以止损，但保留操作者、原因、影响范围、快照和复盘任务。断网客户端不能保证瞬时撤回，控制台需显示下发/确认覆盖，不宣传绝对“秒级全网回滚”。
- 正常扩大流量依赖应用健康、错误率/延迟、执行率和数据质量；业务指标的自动动作另设持有时间、最小样本和经过验证的规则，避免噪声触发来回切换。
- 对策略参数实施依赖检查、模型可用性探测与 shadow 验证。任意不可逆副作用不能仅靠开关“回滚”解决，应在业务实现上提供兼容与补偿策略。
- 企业结构：单企业部署，平台 → 项目 → 环境；工作空间是管理边界；Domain 切分流量，Layer 定义参数子集，不能替代权限边界。后台所有数据、配置、缓存、队列、导出、对象存储与服务密钥都按项目/环境隔离。
- RBAC 可先设管理员、实验负责人、研发接入者、分析师、审批者、只读；大客户再加资源级 ABAC、SSO/SCIM、短期机器凭证、审计导出和地域驻留。
- 审计记录 who/when/why、before/after、审批人、源头（UI/API/GitOps）、发布结果和实际生效覆盖；结果快照带分析代码/指标/源数据 watermark 版本，支持复现。
- V1 不预先承诺固定存储/消息/计算供应商；高 QPS 决策平面、控制平面、事件采集和分析计算要隔离容量及故障域。

## 8. 建议优先级与待验证假设

**V1 必须有：** Domain/Layer/Parameter/Experiment 模型；重叠与非重叠域；参数归层及跨层校验；三类实施模板；统一 SDK/API；稳定随机单元与先域后层分流；曝光契约；中心指标；A/A/SRM；固定周期结果；版本审批与 kill switch；项目/环境权限；决策调试器（展示域、层、实验、variant 与回退原因）。

**下一阶段：** 生产递归分流服务、共享对照、发布层完整执行、SDK 扩展、CUPED、序贯推断、身份桥接、层间交互诊断、复杂策略依赖、组织级实验方法、长期 holdout。Bandit/自动优化应与因果 AB 结论有明确产品边界。

仍需与业务验证：现有登录/匿名身份与埋点体系、主要语言与客户端、日活及决策 QPS、首屏延迟预算、数据仓库和实时链路、项目权限边界、模型发布链路、通常能接受的实验窗口、行业数据驻留限制。没有这些输入前，延迟、可用性、回滚时效和上线工期只能写成待压测目标。
